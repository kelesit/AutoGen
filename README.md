# Playbox Studio — 从业务需求到技术落地的全栈演示

参考 Playbox 的模板探索、创作任务、作品库和积分结构制作的独立 demo，与原网站无关联。采用非露骨的摄影素材，不复用原站内容或代码。

**定位：向合作方展示技术方案如何从业务需求出发，经过规则定义、系统设计与功能实现，再用正常流程和故障场景验证。** AI 输出使用固定演示样片，不是真实生成结果。

## 项目命题

管理员发布动作模板；用户选择模板、上传图片、确认积分成本并提交任务；系统执行任务、保存结果，最终交付可播放的作品。用户需要知道任务进展与积分去向，管理员需要能够纠正模板、查看异常并追溯处理过程。

业务闭环是：**发布模板 → 准备素材与报价 → 提交并冻结积分 → 执行任务 → 保存作品并结算 → 查看或删除作品**。其中“提交成功”“生成成功”和“作品已交付”是不同事件。本项目除了让这条流程可操作，也验证异常情况下任务和积分仍然正确。

## 从业务闭环拆分关键步骤

按责任方交接、业务结果形成和积分变化拆分步骤。每一步明确需要什么输入、由谁完成什么动作，以及什么结果允许流程继续，用这些边界作为后续风险分析的依据。

| 关键步骤 | 责任方 | 输入与动作 | 完成标志 | 任务与积分变化 |
| --- | --- | --- | --- | --- |
| 1. 发布模板 | 管理员 | 准备动作参考、示例成片、图片槽位、Prompt 和输出规格，发布模板。 | 用户能够发现并选择可用模板。 | 尚无用户任务，不涉及用户积分。 |
| 2. 选择模板 | 用户 | 浏览模板说明、示例效果和输入要求，选定本次创作的模板。 | 明确要使用的模板并进入创作。 | 尚无任务，不冻结积分。 |
| 3. 准备素材与参数 | 用户、系统 | 按模板槽位上传图片，选择输出规格；系统检查输入是否满足要求。 | 形成可用于报价和提交的一组素材与参数。 | 尚无任务，不冻结积分。 |
| 4. 获取报价并确认 | 系统、用户 | 系统根据所选规格给出积分报价；用户核对本次输入、规格与费用。 | 用户确认本次创作内容及积分成本。 | 确认报价本身不创建任务，也不冻结积分。 |
| 5. 提交并受理任务 | 系统 | 接收用户提交，复核模板、素材、报价与余额，固定本次任务的输入和价格。 | 任务已创建、具有可查询的任务编号，并进入排队。 | 创建任务并冻结对应积分；这是“提交成功”。 |
| 6. 提交生成并确认接单 | 系统、生成供应商 | 系统按任务中固定的配置和素材发起生成，取得供应商接单结果。 | 确认供应商已受理，并关联外部任务编号。 | 任务进入生成中，积分继续冻结。 |
| 7. 执行生成并取得结果 | 生成供应商、系统 | 供应商执行生成，系统跟踪进展并取得生成结果信息。 | 确认生成成功，结果可供系统保存。 | 任务进入结果保存阶段，积分继续冻结；这是“生成成功”。 |
| 8. 保存并校验结果 | 系统 | 获取生成文件，保存到系统管理的存储，执行文件校验。 | 结果文件已保存并通过当前校验，可用于建立作品。 | 单独完成文件保存尚未完成任务，也不结算积分。 |
| 9. 交付作品并结算 | 系统 | 将已保存的结果建立为用户作品，提供播放与下载入口，同时完成任务和积分结算。 | 作品进入用户作品库，任务与结算记录一致。 | 任务完成，冻结积分转为实际消耗；这是“作品已交付”。 |
| 10. 查看与使用作品 | 用户、系统 | 用户查看任务结果与积分流水，播放或下载自己的作品。 | 用户能够取得作品，并了解本次任务的积分去向。 | 查看、播放或下载不再次扣分。 |
| 11. 删除作品（可选） | 用户、系统 | 用户删除自己的作品；系统撤销后续访问，并清理无有效占用的文件。 | 作品不再展示，新的播放与下载请求被拒绝；文件清理可随后完成。 | 保留任务完成事实和积分记录，不退款。 |

这条主线有三个不同的成功节点：**提交成功表示平台已受理；生成成功表示供应商已产出结果；作品已交付表示系统已保存结果、建立作品并完成结算。** 结算不等待用户首次播放，删除也不是完成交付的必要条件。

另需保留三类分支：受理前校验不通过时不创建任务、不冻结积分；受理后确认失败或在允许的排队阶段取消时释放冻结积分；执行结果无法确定或保存暂未完成时保留未完成状态和冻结积分，进入恢复或核查流程。

以上描述业务步骤及其完成标准。前端获取并展示服务端报价，新任务必须携带确认金额和价格版本，后端重算并核对一致后才受理。当前演示通过固定样片验证交付流程，文件校验仅覆盖基本格式与体积；实现边界详见“当前范围与后续工作”。

## 从业务风险确定规则

| 业务风险 | 项目采用的规则 |
| --- | --- |
| 管理员修改模板后，已创建但未完成的任务误用新配置 | 任务在提交时固定模板版本、素材和价格快照；后续编辑不改变已有任务。 |
| 请求缺少报价确认信息，或用户确认后价格发生变化 | 新任务必须携带确认金额和价格版本；缺失、无效或与服务端重算报价不一致时拒绝受理，不创建任务、不冻结积分。 |
| 用户重复提交，或浏览器没有收到提交响应 | 相同请求标识与参数返回原任务；浏览器刷新后先查找原任务。 |
| 供应商可能已接单，但响应丢失 | 先按原业务单号查单；无法可靠判断时进入人工核查，不自动重新生成或退款。 |
| 生成完成，但视频尚未保存或无法播放 | 生成与保存分阶段；文件保存并校验成功后才创建作品、结算积分。 |
| 执行进程退出、事件重复或晚到 | 任务持久保存，由 Worker 恢复；状态和账务只允许合法变更。 |
| 删除作品或素材后仍可从旧入口读取 | 按归属和有效引用授权；作品删除后阻止新的播放与下载请求，后台清理无占用文件。 |

创建任务时冻结积分；作品交付后结算，确认失败或排队取消后释放。只有尚未向供应商提交的排队任务可以取消。供应商模拟成本与用户积分分开记录，用户积分释放不代表供应商成本消失。

## 从规则拆出功能需求

每个业务步骤进一步明确使用角色、前置条件、正常流程、异常分支和可观察的完成标准。详见[功能需求与验收清单](./docs/functional-requirements.md)：覆盖 11 个主流程步骤，以及模板维护、任务取消和管理员异常处理，并区分现有测试覆盖、待专项验收和待完善项。

| 业务阶段 | 要完成的事 | 对应的功能 |
| --- | --- | --- |
| 准备供给 | 管理员提供并维护可用模板 | 上传动作参考与独立示例成片，配置图片槽位、Prompt 和规格；模板新增、搜索、筛选、分页、编辑、上下架和不可恢复删除；发布草稿恢复。 |
| 发现与准备 | 用户找到模板并提供有效输入 | Explore 浏览与收藏、登录后继续原操作、按槽位上传图片、参数校验；换图失败时阻止沿用旧图提交。 |
| 报价与提交 | 用户了解成本并发起一次创作 | 前端展示服务端报价；服务端重算费用、检查素材与余额，在同一事务中创建任务、冻结积分并保存执行记录。 |
| 执行与恢复 | 网页关闭或进程重启后，任务仍能继续 | 独立 Worker、持久任务表、租约、并发控制、查单恢复、限流退避和人工核查状态。 |
| 交付与追溯 | 用户取得作品并看清任务结果 | 私有文件保存与校验、独立作品记录、Collection 播放/下载/删除、任务时间线和积分流水；管理员查看调用记录与恢复阶段。 |

模板的参考视频、Prompt、槽位或规格变更创建新版本；标题、说明、分类或预览修改不创建生成版本。模板删除不可恢复，但既有任务仍按提交时的快照执行。作品删除不改变任务已完成的事实，也不退款。详细规则见[重构基线](./docs/refactor-baseline.md)和[模板结构](./docs/motion-template.md)。

## 技术方案如何支撑这些规则

系统保持单机模块化：React + Vite+ 前端、Express API、SQLite 业务数据库、独立 Worker、私有本地媒体文件，以及使用独立数据库的本地模拟供应商。API 按模板、生成、账务、作品和资产划分业务服务。任务表同时承担持久队列职责；当前演示没有引入 Redis、微服务或跨机器共享存储。

任务创建、素材引用、积分冻结和执行记录放在同一数据库事务中，避免“积分已冻结但任务未入队”。Worker 在短事务内领取任务，外部调用不占用数据库事务；进程退出后由租约和持久状态恢复。文件系统与数据库不能组成一个事务，因此输出资产先保存和校验，再建立作品、完成任务并结算；清理流程可重试。

统一资产记录区分图片、参考视频、预览和作品，并按业务入口控制读取权限。公开预览不意味着参考视频或用户图片公开；当前模板、未结束任务与有效作品决定文件是否保留。新上传但未被引用的文件过期后清理，历史记录用于追溯，不永久占用文件。详见[媒体生命周期](./docs/media-lifecycle-design.md)。更完整的状态机、账务不变量和恢复协议见[架构说明](./ARCHITECTURE.md)。

## 验证与演示

建议先按[演示步骤](./DEMO_GUIDE.md)走通管理员发布模板、普通用户提交任务并取得作品。页面上可演示并核对的异常包括：

1. 供应商已接单但响应丢失：查回原外部任务，最终只提交和结算一次。
2. 生成成功但首次保存失败：重试保存，最终只有一件作品、一次结算。
3. 浏览器丢弃提交响应：刷新后找回原任务，不重复创建或冻结。
4. 无法可靠查单：进入人工核查，展示自动恢复的边界。

重复、乱序事件与进程退出由下方自动化测试验证。前者不再提供页面注入按钮；测试直接检查任务终态、作品数量、结算流水和余额不变量。

```sh
npm test
npm run build
```

构建包含严格类型检查和未使用变量/参数检查。测试使用独立临时数据（包括隐藏 `.data` 子目录），覆盖管理员发布/修改/下架→普通用户生成→作品库、视频播放与下载、接口权限、幂等、余额不变量、上传隔离、重启恢复、全局并发、失败预算、重复/乱序事件，以及真实子进程在接单后和文件落盘后退出的恢复。

## 运行演示

需要 Node.js 24+。在项目目录执行：

```sh
npm ci
npm run dev
```

打开 http://127.0.0.1:5173 。`npm ci` 安装依赖；`npm run dev` 启动前端、API 和 Worker。前端开发服务器通过代理访问 8787 端口的 API。

也可以先构建，再由 API 提供构建好的页面：

```sh
npm run build
npm start
```

此时打开 http://127.0.0.1:8787 。`npm start` 启动 API 和 Worker。两种方式默认仅监听本机，不向外网公开。需要额外执行进程时可单独运行 `npm run worker`。

| 角色 | 邮箱 | 密码 |
| --- | --- | --- |
| 普通用户 | demo@playbox.local | PlayboxDemo2026! |
| 管理员 | admin@playbox.local | PlayboxAdmin2026! |

登录弹窗可自动填入演示账户，也支持注册新用户。每个新账户初始拥有 300 演示积分，重启或再次登录不会重置余额。管理员可以查看管理数据并执行有记录的任务恢复和事件重放；普通用户不能调用管理接口。这些凭据仅供本地演示，不适合公开运营。

默认数据在 `.data-v2/`：`playbox.sqlite` 是业务数据库，`provider.sqlite` 是模拟供应商数据库，`assets/` 是私有业务媒体目录；重启不会清空。旧 `.data/` 保留但不读取，也不迁移。`DATA_DIR` 可指定开发目录；API 与 Worker 必须使用相同目录。`PORT`、`HOST`、`APP_ORIGIN`、`COOKIE_SECURE` 控制 API 环境。开发代理固定指向 8787，修改 API 端口时还需同步修改 `vite.config.ts`。

## 当前范围与后续工作

生成适配器能持久记录外部接单，并注入超时、限流、生成失败和下载失败，但输出始终是固定 CC0 花卉视频；不会根据图片或 Prompt 生成内容，实际视频也不随所选规格变化。模拟调用不经过公网，不能代替真实供应商协议或网络联调。演示积分没有货币价值，供应商成本单位 `mock_units` 也不是真实报价。

当前只做管理员模板目录、用户选模板生成和作品交付；没有用户投稿审核、训练、真实支付、订阅或创作者分成。任务所有者当前可在任务快照中看到 Prompt。作品和素材列表最多展示 100 条。详见[文档与代码核对](./docs/doc-code-audit-2026-09-24.md)。

作品与模板删除不可恢复，任务和积分记录保留。作品删除阻止后续播放与下载请求，但不能撤回已开始的传输或已下载副本。新上传的参考、预览和图片在无有效占用且超过 24 小时后进入清理候选，到期不等于立即失效。视频目前只做基本格式与体积校验。真实服务接入还需验证幂等与查单语义、媒体传输、完整视频解析与转码、支付、对象存储及生产容量。
